# S16 · Deployment

**Status:** implemented · **Fidelity:** no application change (the API and the web app behave as in S14 and
S15). Depends on S10 and S11; phase 3 depends on S14.

## Goal
Run the API, the web app and MongoDB on the internet for personal use at no cost: free plans only,
no payment method on any account, and as few accounts as possible. The platform is described as
code in this repository, so a deployment change travels in the same pull request as the code it
needs, and a merge to `main` that passes CI deploys it.

## How this spec is organized
Deploying mixes changes to the repository with steps only the owner can take in the Render, Atlas
and GitHub dashboards. They are kept apart:
- **Repository changes** are what plan phases implement.
- **Manual runbook** steps (`R1`, `R2`, …) are done by the owner, never by an agent. Each phase lists
  the steps it requires before it starts and the ones that follow its merge.
- A plan made from this spec keeps the runbook as its own section, outside the phases, with its own
  checkboxes, so an unchecked runbook step never makes a finished phase look pending. A phase whose
  required steps are unchecked stops and asks the owner instead of starting.

## Platform
| Piece | Where | Plan |
|---|---|---|
| API (`Dockerfile`) | Render web service, region Frankfurt | Free |
| Web app (`web/`, S14) | Render static site | Free |
| MongoDB | MongoDB Atlas cluster on AWS `eu-central-1` (Frankfurt) | Free |
| Keep-alive | GitHub Actions scheduled workflow | Free (public repository) |

- Two accounts: Render and Atlas, both created with GitHub. No card is given to either, so neither
  can charge.
- The API and Mongo share a region, so a query costs milliseconds; Frankfurt is about 30–40 ms from
  Spain.
- Known limits of the free plans, accepted:
  - The API has 0.1 CPU and 512 MB of memory. A run with those limits peaked at 110 MB and the
    startup scrape took about 20 s.
  - Render gives 750 instance hours a month: enough for **one** free web service always on. A second
    free web service running at the same time would use them up before the month ends.
  - Render stops a free web service after 15 minutes without inbound requests and takes about a
    minute to start it again. The keep-alive prevents it.
  - The free web service has no persistent disk, no shell and no fixed outbound IP.
  - The Atlas free cluster has 512 MB of storage and no backups.

## Repository changes

### `render.yaml`: API service
A Render Blueprint at the repository root. It holds no secret.
- Name `daily-trends-api`, runtime Docker from the root `Dockerfile`, plan free, region Frankfurt.
- Health check path `/status` (S01): it answers 200 without reading Mongo.
- Deploys automatically after the CI checks of the commit pass on `main`.
- Build filter: only changes under `src/`, `pyproject.toml`, `uv.lock`, `.python-version`,
  `Dockerfile` and `.dockerignore` deploy it. A change to `web/`, `specs/`, `tests/` or docs alone
  does not.
- Environment:

| Variable | Value |
|---|---|
| `ENV` | `production` |
| `MONGO_URL` | not in the file (`sync: false`): set in the Render dashboard (R4) |
| `AUTH_SECRET_KEY` | generated by Render once, when the service is created |
| `FORWARDED_ALLOW_IPS` | `*` |

- `PORT` is set by Render and read by the settings (I04). The other settings keep their defaults:
  the scheduler on, every 2 hours (S10).
- `FORWARDED_ALLOW_IPS` lets the server trust the `X-Forwarded-Proto` header of Render's proxy,
  which terminates HTTPS. Without it, a URL the API builds (a redirect) would say `http://` and the
  browser would block it as mixed content.
- Regenerating `AUTH_SECRET_KEY` logs every administrator out (S11).

### `render.yaml`: web service
- Name `daily-trends-web`, a static site with root directory `web/`.
- Build command: `corepack pnpm install --frozen-lockfile && corepack pnpm build`; published
  directory `dist`. pnpm runs through Corepack at the version of `packageManager`, without
  `corepack enable`: Render's `/usr/bin` is read-only, so the shims it writes there fail the build.
  Node comes from `web/.nvmrc` (S14), or from `NODE_VERSION` when Render does not read it, with the
  same version.
- `VITE_API_BASE_URL` is the public URL of the API service, known after R4. It is not a secret, so it
  is a literal value in the file. Vite reads it at build time: changing it needs a new build.
- Every path that is not a file is rewritten to `/index.html`, so a reload on `/feeds?…` or a CMS
  route opens the app.
- Headers: `Cache-Control: public, max-age=31536000, immutable` on `/assets/*` (file names carry a
  content hash) and `Cache-Control: no-cache` on `/index.html`.
- Deploys automatically after the CI checks pass on `main`. Build filter: only changes under `web/`.

### Keep-alive workflow
> Superseded by [S17](S17-reliable-keep-alive.md): GitHub drops most scheduled runs, so a
> cron-job.org job is the keep-alive and this workflow is deleted.

- `.github/workflows/keep-alive.yml` runs every 10 minutes and on demand. It requests
  `GET <API_URL>/status`, with a timeout long enough to cover a cold start and a few retries.
- `API_URL` is a repository variable, not a secret: it is public anyway.
- When `API_URL` is not set, the job is **skipped**, not failed, so merging the workflow before R7
  raises no alarm.
- A failed run marks the workflow red and GitHub emails the owner. That is the only alerting.

### CI
- `ci.yml` also runs on `push` to `main`, so Render sees the checks of the merged commit before it
  deploys it.

### Documentation
- `README.md` gains a *Deployment* section: the platform table, the free-plan limits and the manual
  runbook below, so the steps live next to the code. Each phase adds the part it enables. Once S16
  was done, the section moved to `docs/deployment.md`, linked from `README.md`.
- `AGENTS.md` notes that `render.yaml` and `keep-alive.yml` describe production, that agents never
  run runbook steps, and that an API contract change is additive first.

### Contract between the two services
- The API and the web app deploy separately, even when one pull request changes both, so for a few
  minutes the deployed web app can talk to the previous API or the other way round. A change to the
  API contract is therefore additive first (new field or route), then the web app uses it, then the
  old shape is removed in a later change.
- The browser calls the API from the web app's origin with a bearer token and no cookies. CORS
  already allows any origin and the `Authorization` header (S11), so the API does not change.

## Manual runbook
Done by the owner, in this order. The phase each step belongs to is in brackets.

1. **R1 · Atlas cluster** [before phase 1]
   - A free cluster on AWS `eu-central-1`.
   - A database user only for the API, with a long random password and read and write access to the
     `daily-trends` database.
   - Network access from `0.0.0.0/0`: the free Render service has no fixed IP. The database user's
     password is what protects it.
   - The connection URL names the database, because the API takes it from the URL:
     `mongodb+srv://<user>:<password>@<cluster>/daily-trends?retryWrites=true&w=majority`.
   - The migrations run when the API starts (I07), so the empty cluster needs no preparation.
2. **R2 · Scraping from Render** [before phase 1]
   - A web service created by hand in the Render dashboard, named `daily-trends-api-spike`, from this
     repository's `Dockerfile` on `main`, plan free, region Frankfurt, with the variables of the API
     service (`MONGO_URL` from R1, any `AUTH_SECRET_KEY` of 32 characters or more).
   - Its logs show the migrations, then `Scheduled scraping saved N feeds` and a 200 for each of the
     five sources.
   - A source that fails from Render is reported before phase 1 starts. The fix is a new improvement
     spec, and phase 1 can still go ahead without it.
3. **R3 · Remove the spike** [before phase 1]
   - Delete `daily-trends-api-spike`, so it neither shares the 750 free hours nor takes a name.
4. **R4 · Create the Blueprint** [after phase 1 is merged]
   - In Render, a new Blueprint from this repository on `main`. When it asks for `MONGO_URL`, the URL
     from R1.
   - The first deploy passes its health check. Note the API URL (`https://<api>.onrender.com`); R7 and
     phase 3 need it.
5. **R5 · First administrator** [after R4]
   - The free Render service has no shell, so the administrator is created from a developer machine
     against Atlas. The variables go on the command line so that the local `.env` does not apply;
     `create-admin` signs no token, so any key of 32 characters or more works:

     ```bash
     ENV=production MONGO_URL='mongodb+srv://…/daily-trends?…' \
       AUTH_SECRET_KEY=unused-here-but-required-in-production \
       uv run daily-trends-py create-admin --email <email>
     ```

   - The password is long: the login has no rate limit or lockout (S11).
6. **R6 · Check the API** [after R5]
   - `GET /status` answers 200, `/docs` loads, `/feed/home` answers feeds, and `/auth/login` with the
     administrator answers a token.
7. **R7 · Keep-alive variable** [after phase 2 is merged]
   - The repository variable `API_URL` with the URL from R4. A manual run of the keep-alive workflow
     is green.
   - A day later, every scheduled run is green and the API logs show no restart.
8. **R8 · Check the web app** [after phase 3 is merged]
   - Render's Blueprint sync creates `daily-trends-web` and its first build passes.
   - The front page shows feeds, a reload on a deep route opens the app, and, once S15 exists, the
     administrator logs in to the CMS and creates a feed.

ready.

## Testing approach
- These phases change configuration and documentation, not application behavior, so they have no
  red-green-refactor cycle. The plan records this, as `ai-project-tdd` asks for behavior that cannot
  reasonably be test-first.
- No test parses `render.yaml` or the workflows: their correctness is what Render and GitHub do with
  them, which the runbook checks.
- Each phase's verification is the quality gate from `AGENTS.md` (unchanged by these files), plus
  the web quality gate of S14 in phase 3, plus the runbook steps that follow its merge.

## Out of scope
A custom domain, restricting CORS to the web app's origin, login rate limiting, database backups,
monitoring and alerting beyond failed keep-alive runs, a staging environment, preview environments,
hiding `/docs`, validating `render.yaml` in CI, and any paid plan.

## Edge cases
- `MONGO_URL` missing in Render → the API does not start (I04), the deploy fails its health check and
  the previous deploy keeps serving.
- Atlas URL without `/daily-trends` → the API cannot pick a database and does not start.
- A merge to `main` that only changes `specs/` → no service deploys.
- A merge that changes `web/` and `src/` → both deploy, each after CI passes.
- Phase 2 merged and R7 not done yet → the keep-alive job is skipped every 10 minutes, with no
  failure email.
- The keep-alive misses a run (GitHub delays scheduled runs under load) → the API stops after 15
  minutes; the next request or keep-alive run starts it in about a minute, and a scrape runs at
  startup (S10). The feed identity rules make it repeated work, not repeated feeds.
- No commit for 60 days → GitHub disables the scheduled workflow; a commit or re-enabling it turns
  it back on.
- A newspaper blocks Render's IPs → that source fails in every run and the others are saved (I02).
- A rollback of the API in the Render dashboard does not undo a migration (I07): migrations stay
  additive so the previous version still runs.
- Reload on `https://<web>.onrender.com/feeds?category=POLITICS` → the app opens on that page.
